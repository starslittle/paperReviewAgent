# DocAgent 科研项目概括（详细版）

## 一、项目定位与学术背景

### 1.1 项目名称与出处

- **项目名称**：DocAgent（文档智能体）
- **论文标题**：_DocAgent: An Agentic Framework for Multi-Modal Long-Context Document Understanding_
- **论文链接**：https://aclanthology.org/2025.emnlp-main.893.pdf

### 1.2 研究动机与要解决的问题

现有大语言模型（LLM）在文档理解与问答上虽有进展，但存在三大局限：

| 挑战               | 具体表现                                                     |
| ------------------ | ------------------------------------------------------------ |
| **上下文长度受限** | 多数模型 4K–32K tokens，无法直接处理百页级长文档             |
| **多模态利用不足** | 文档含文本、图表、公式等，需要综合理解，而非仅文本或简单 OCR |
| **全局连贯性丢失** | 简单 Map-Reduce 分块会破坏章节间逻辑与一致性                 |

DocAgent 的目标是：在**不依赖超长上下文**的前提下，对**超长、多模态文档**进行**结构化理解与审查**，并尽量接近人类阅读与判断水平。

---

## 二、核心思想：模拟人类阅读过程

系统设计对应人类阅读的五个步骤：

| 人类阅读行为                | DocAgent 对应设计                                          |
| --------------------------- | ---------------------------------------------------------- |
| 1. 浏览大纲，确定重点章节   | **树状大纲**：从文档提取结构化 XML 层次，便于按章节定位    |
| 2. 精读章节，提取细节       | **工具化接口**：按需检索章节内容、图表，而非一次性灌入全文 |
| 3. 多模态理解（图表与正文） | **视觉审查 Agent**：结合页面图与正文做图文一致性判断       |
| 4. 交叉验证不同来源信息     | **Reviewer + 记忆银行**：跨章节事实存储与冲突检测          |
| 5. 全局推理与逻辑一致性     | **层次化 Map-Reduce**：先分章审查再全局汇总，保证逻辑一致  |

整体特点：**短上下文、多轮调用、工具化检索**，从而支持 100+ 页文档的审查。

## 三、系统架构总览

### 3.1 三阶段流水线

```
Phase 1: 数据预处理  →  Phase 2: 多智能体协作审查  →  Phase 3: 报告生成与可视化
```

- **Phase 1**：PDF → 结构化 XML 树 + 页面图像 + 图表资源（`data.pkl`、`figures/`、`page_images/`）
- **Phase 2**：DocReader + 规范性 / 逻辑 / 视觉 三类 Agent + 记忆银行 + 可选 Reviewer
- **Phase 3**：输出 `review_*.json`、`report_*.html`、`outline_*.xml`、`tree_*.xml`

### 3.2 主要模块与职责

| 模块                | 功能                                         | 输入                             | 输出                   |
| ------------------- | -------------------------------------------- | -------------------------------- | ---------------------- |
| **预处理**          | PDF 结构化提取与增强                         | 原始 PDF                         | data.pkl、图像、XML 树 |
| **DocReader**       | 动态文档检索（大纲、章节、搜索、图片、表格） | XML 树与资源路径                 | 按需返回内容片段       |
| **Normative Agent** | 格式与结构规范审查                           | 大纲 + 正文前段                  | 规范性问题列表         |
| **Logic Agent**     | 逻辑一致性审查（含摘要、事实、冲突）         | 分章节内容                       | 逻辑问题 + 记忆银行    |
| **Vision Agent**    | 图文一致性审查                               | 图片 + 前后页截图 + Caption/正文 | 视觉问题列表           |
| **记忆银行**        | 跨章节事实存储与冲突检测                     | 章节摘要与实体/数值/时间/论断    | 冲突项                 |
| **报告生成**        | 结果可视化                                   | 审查 JSON                        | HTML 报告              |

## 四、数据预处理模块

### 4.1 预处理流程（四步）

1. **Step 1：PDF 内容提取**
   - 支持 **Adobe PDF Services** 或 **MinerU** 等，得到中间结构化数据（如 `structuredData.json`）
   - 输出：`extract_output/{doc_id}/`（含 JSON、figures、tables 等）

2. **Step 2：标题增强与修正**
   - 可选 **PaddleOCR** 或 **视觉大模型（VLM）** 增强标题检测
   - 对比 Adobe/MinerU 提取结果，补充遗漏标题、降级误识别标题
   - 输出：`data.pkl`（Pandas DataFrame，含 style、table_id、para_text 等）

3. **Step 3：生成页面图像**
   - 使用 PyMuPDF 将每页渲染为 PNG（如 150 DPI）
   - 供 Vision Agent 做页面级视觉验证

4. **Step 4：构建 XML 树**
   - 根据 `data.pkl` 中的 Heading 层级构建层次化 XML（Section/Paragraph/Image/Table/Caption 等）
   - 每个节点带 `section_id`、`page_num` 等，便于 DocReader 按章节/页码检索

### 4.2 数据结构要点

- **DataFrame**：`style`（如 "Heading 1"/"Normal"/"Image"/"Table"）、`table_id`、`para_text`
- **XML 树**：多级 `<Section>` 嵌套，内含 `<Heading>`、`<Paragraph>`、`<Image>`、`<CSV_Table>`、`<Caption>` 等，均带页码与 ID

## 五、多智能体协作框架

### 5.1 Agent A：规范性审查（Normative Agent）

- **输入**：`get_outline()`（前 100 页大纲）+ 正文前若干字符（如 6000 字）
- **检查项**：目录完整性、章节编号连续性、图表编号与引用、页码与标题格式、必备模块（摘要/参考文献等）
- **输出**：规范性问题列表（含 issue_type、severity、page、quote、suggestion）
- **创新点**：对“缺少章节”等易误报项，可调用 **视觉模型看页面截图** 做二次验证，减少 PDF 解析错误导致的误报

### 5.2 Agent B：逻辑审查（Logic Agent）— 层次化 Map-Reduce

- **Phase 1 - 章节选择**：LLM 根据 Outline 选出最重要的若干章节（如 8 个），避免附录/参考文献等冗余
- **Phase 2 - Map（分章节审查）**：
  - 对每个选中章节调用 `get_section_content(section_id)` 获取完整 XML 子树
  - 做微观逻辑检查（论证跳跃、前后矛盾、语言学术化、段落衔接）
  - **提取章节摘要** 写入 **Logic Memory**
  - **细粒度事实提取**（实体、数值、时间、论断）写入 **Fact Store**
- **Phase 3 - Reduce（全局一致性）**：
  - 基于各章节摘要做“摘要 vs 结论”“方法 vs 实验”“数值一致性”等检查
- **Phase 4 - 冲突检测**：
  - 对 Fact Store 中同一 key 的多个 value 做冲突检测（如同一指标在不同章节数值不一致）

**记忆银行**：Logic Memory 存章节摘要；Fact Store 存实体/数值/时间/论断的跨章节索引，用于发现矛盾。

### 5.3 Agent C：视觉审查（Vision Agent）

- **输入**：对每张图，提供 **目标图片** + **当前页** + **前一页** + **后一页** 截图（三页窗口策略），以及 Caption、前后段落文本
- **任务**：判断图片内容与 Caption、正文描述是否一致，是否存在图文矛盾
- **模型**：多模态大模型（如 Qwen3-VL-Flash）
- **创新点**：三页窗口解决 Caption 跨页、图在页尾而说明在下一页等问题；可配置最大图片数（如 50）以控制成本

### 5.4 可选 Reviewer

- 用于 QA 等任务的答案交叉验证，本项目审查流水线中未默认启用，但保留接口。

## 六、文档阅读器（DocReader）

- **核心职责**：不一次性加载全文，而是通过**工具接口**按需返回内容，模拟“跳读”。
- **主要接口**：
  - `get_outline_root()`：简化大纲（前 100 页，段落仅首句）
  - `get_section_content(section_id)`：指定章节完整 XML 子树
  - `search(keyword)`：关键词检索
  - `get_image(image_id)` / `get_page_image(page_num)` / `get_table_image(table_id)`：返回 Base64 图像
- **实现**：基于 `data.pkl` 构建 XML 树，并维护 `section_dict`、`image_path_dict`、`table_image_path_dict` 等索引。

---

## 七、报告生成与可视化

- **输入**：`review_{doc_id}.json`（含 normative/logic/vision 的 thinking 与 issues、可选 toc_suggestion）
- **输出**：
  - **report\_{doc_id}.html**：交互式报告，含综合评分、按规范性/逻辑性/视觉问题分类、严重程度统计、可折叠的 AI 思考过程、按页码排序的修改建议
  - **outline\_{doc_id}.xml** / **tree\_{doc_id}.xml**：大纲与完整树（调试与复现用）
- **分类逻辑**：按 `issue_type` 与关键词（规范/格式/目录/编号、逻辑/语言/连贯、图文一致性）及 `image_id` 将 issues 归入规范性/逻辑性/视觉/其他，并在各分类内按页码排序。

## 八、你当前项目中的扩展与落地

在论文开源实现基础上，你做了**面向本科毕业论文（尤其是计算机类）的审查落地与优化**，主要包括：

### 8.1 摘要专项审查

- **文档**：`docs/摘要审查使用指南.md`、`docs/摘要审查功能实施总结.md`
- **要求**：摘要须包含 **研究背景 → 技术方案/功能介绍 → 研究成果** 三部分；关键词不少于 4 个（中英文），格式与主题相关
- **测试**：`test_abstract_review.py` 可单独跑摘要审查

### 8.2 论文类型差异化审查

- **文档**：`docs/论文类型差异化审查设计.md`
- **类型**：**算法类**（侧重算法改进、实验与性能） vs **系统设计类**（侧重技术栈、功能模块、测试与体验）
- **实现**：`review_runner.py` 支持 `--thesis-type`：`auto` / `system` / `algorithm`，用于在提示与检查重点上做差异化

### 8.3 问题分类与报告修正

- **文档**：`docs/规范性问题分类错误分析.md`
- **问题**：规范性问题被误分到视觉/其他（如因 `image_id` 优先、或“目录结构”未纳入规范性类型）
- **修正**：在 `generate_report.py` 中扩展 `normative_types`（如含“目录结构”“章节结构”“编号问题”“格式问题”），并**先按 issue_type 与关键词分类，再在无明确类型时用 img_id 归入视觉**，避免误分类

### 8.4 图文一致性判断可解释性

- **文档**：`docs/图文一致性判断原因分析.md`
- **内容**：分析“原文片段”过短（如仅“3.”）、以及“图像证据强度高于文字主张”等规则（如 rule3）的触发条件与强度计算逻辑，便于调试与解释 Vision Agent 的决策

### 8.5 预处理与数据

- **预处理**：支持 MinerU、Adobe 等；可选 OCR/VLM 标题增强；步骤封装为脚本（如 `scripts/run_pipeline.ps1`、`preprocess/run_pipeline.py`）
- **数据**：`data/` 下按文档 ID 分目录（如 `bylw-ckg`、`bylw-clx` 等），对应多份毕业论文
- **结果**：`sample_results/` 内存放各文档的 `review_*.json`、`report_*.html` 等

## 九、技术栈与依赖

| 类别           | 技术/服务                                                |
| -------------- | -------------------------------------------------------- |
| PDF 提取       | Adobe PDF Services / MinerU                              |

| 配置           | python-dotenv，`.env` 中配置 Adobe、DASHSCOPE_API_KEY 等 |

## 十、关键创新点小结

1. **OCR/视觉增强的标题修正**：弥补 PDF 提取对非标准标题的漏检与误检
2. **规范性问题视觉验证**：对“缺失章节”等用页面截图二次判断，降低误报
3. **三页窗口多模态输入**：解决图注跨页、上下文不完整问题
4. **层次化 Map-Reduce + 记忆银行**：分章审查 + 摘要与事实存储 + 全局一致性与冲突检测
5. **工具化动态检索**：DocReader 按需返回大纲/章节/图片，控制单次上下文长度与成本

## 十二、运行流程速览

1. **预处理**（任选一种方式）
   - 通用：`preprocess/` 下依次执行 1 提取 → 2 处理 → 3 页面图 → 4 建树
   - 指定文档（如 bylw-pgy）：`scripts/run_pipeline.ps1 -DocName bylw-pgy` 或按 README 分步执行

2. **审查**
   - 单文档：`python review_runner.py --doc-id <doc_id>`
   - 可选：`--thesis-type auto|system|algorithm`

3. **报告**
   - `python generate_report.py --doc-id <doc_id>`
   - 在浏览器中打开 `sample_results/report_<doc_id>.html`

## 十三、局限与后续方向（来自架构文档）

- 依赖 PDF 质量，扫描版需更强 OCR
- 数学公式未专门建模（可接 MathPix/LaTeX OCR）
- 主要面向中文论文，英文需调 Prompt
- 复杂表格可能解析不理想
- 当前为串行处理，可考虑流式或并行优化

**总结**：你的科研项目是在 **EMNLP 2025 DocAgent** 的基础上，面向**本科毕业论文（含摘要、规范、逻辑、图文一致性）**做了完整落地，并针对**问题分类、报告展示、摘要与论文类型差异化**做了文档与实现上的增强，形成了一套可复现的“长文档多模态审查”流水线。
