# 让批改更像老师——报告分析与改进方案

基于对 `sample_results/report/report_bylw-sk.html` 及对应 `review_bylw-sk.json` 的阅读，总结当前输出的特点，并与“老师批改”的典型特征对比，给出可落地的改进建议。

---

## 一、当前输出的特点（简要）

### 1.1 报告结构

- **顶部**：综合评分、严重问题数、建议修改数、问题总数（数字卡片）
- **中部**：AI 思考过程（规范性 / 逻辑 / 视觉）折叠块 + 目录检测与推荐目录
- **底部**：详细修改建议，按类别展开：
  - 📏 规范一致性问题 (5)
  - 🧠 逻辑一致性问题 (40)
  - 🖼️ 图文一致性问题 (17)

### 1.2 单条问题的呈现方式

每条问题大致包含：

- **标题行**：`[目录结构问题] 第 5 页:` + 一句简短描述（如「目录中未见第一章'绪论'」）
- **正文**：
  - 位置：`📍 位置: 第 5 页 | 章节: 缺少第一章`
  - 原文片段/描述
  - **🤖 AI 修改建议**

### 1.3 当前风格归纳

| 维度 | 当前表现 |
|------|----------|
| **身份标签** | 「🤖 AI 修改建议」、类别用「规范一致性」「逻辑一致性」等术语 |
| **标题** | 以类型+页码为主，如 `[目录结构问题] 第 5 页:` |
| **建议措辞** | 偏规范、条款式：「缺少第一章'绪论'，这是程序开发类论文的必需章节。建议在开头添加第一章…」 |
| **语气** | 多用「应」「建议」「必须」；少用「可以」「不妨」「如果…会更好」 |
| **优先级** | 仅用 High/Medium/Low，没有「必改 / 建议改 / 有时间再改」这类老师常用说法 |
| **整体评价** | 无开头的总评、无结尾的总结与鼓励 |
| **肯定与批评比例** | 几乎只有问题，没有「这部分写得不错，但…」的平衡 |

整体上更像**自动检查清单 + 规范说明**，而不是**老师当面或书面批改**。

---

## 二、老师批改的典型特征（对比用）

| 维度 | 老师常见做法 | 与当前的差距 |
|------|--------------|--------------|
| **身份与语气** | 以「老师」或「评阅人」口吻，带一点鼓励 | 当前是「AI 修改建议」，偏机器、偏冷 |
| **总评** | 先有一两句总评：「整体完成度不错」「结构完整，主要在格式和用语上再打磨一下」 | 当前没有总评，直接进入问题列表 |
| **问题表述** | 「第 5 页目录这里少了第一章」比「目录中未见第一章'绪论'」更口语、更像在指位置 | 当前偏书面、偏术语 |
| **建议写法** | 常给**一句最关键的改法**，再补「如果还想更好，可以…」 | 当前常是一段完整规范说明，信息多但重点不够突出 |
| **优先级** | 「这个必须改」「这个建议改」「这个有时间再优化」 | 当前只有 High/Medium/Low，没有中文优先级说明 |
| **肯定 + 批评** | 「摘要结构是完整的，但成果部分可以写得更具体一点」 | 当前几乎只提问题，不提做得好的地方 |
| **措辞** | 多用「可以」「不妨」「试试」「会更好」；少用「应」「必须」 | 当前「应」「建议」多，语气偏硬 |

## 三、改进思路（三层）

### 3.1 第一层：Prompt 层——让 Agent 输出更「老师口吻」

**目标**：在**不改变现有 JSON 字段**的前提下，让 `suggestion`（以及必要时 `quote`）的**内容**更像老师写的。

可在以下位置加入「老师口吻」的约束与示例（具体加在 `agent/prompts.py` 的规范性、逻辑、目录、视觉等 prompt 中）：

1. **角色设定**  
   - 明确写一句：以**本科毕业论文指导教师 / 评阅教师**的口吻写 `suggestion`，语气严谨但温和，避免冷冰冰的条款罗列。

2. **suggestion 写法要求**  
   - 每条建议**先给一句可直接照做的改法**（如「把英文摘要里的 Key words 改成 Keywords，K 大写」），再视需要简短补一句理由或可选优化。  
   - 鼓励使用：「可以」「不妨」「建议」「如果…会更好」「这里…就好」；减少：「应」「必须」「不符合规范」等硬性表述（除非确属硬性规范）。

3. **可选：在逻辑/语言类里加「肯定再批评」**  
   - 若某条问题对应段落/章节有可取之处，可在 suggestion 里先一句话肯定（如「这一段逻辑是顺的」），再写「但…处可以…」。

4. **示例（给模型参考）**  
   - 当前风格：`缺少第一章'绪论'，这是程序开发类论文的必需章节。建议在开头添加第一章，标题为'绪论'或'引言'，包含以下小节：1.1 选题背景与意义…`  
   - 老师风格：`目录里少了第一章「绪论」，需要补上。一般包含 1.1 选题背景与意义、1.2 国内外研究现状、1.3 主要研究内容、1.4 论文组织结构，你可以按学校模板微调。`

这样**无需改报告模板和 JSON 结构**，只靠 prompt 就能让「详细修改建议」里的文字更像老师批改。

---

### 3.2 第二层：报告展示层——总评、优先级、措辞

**目标**：在 `generate_report.py` 和 HTML 里，让**整体观感**更像一份老师给的批改报告。

1. **增加「总评」区块（可选，数据可从合并 issues 生成或由后续 Agent 生成）**  
   - 在「详细修改建议」之前增加一小段**总评**：  
     - 若实现简单版：可根据 High/Medium/Low 数量生成一句总评（如「整体结构完整，主要需注意目录与关键词格式，以及若干处用语可更学术化。」）  
     - 若实现完整版：在 review 流程中增加一步，让 LLM 根据全部 issues 生成 2–3 句「老师口吻总评」，写入 JSON（如 `overall_comment`），再在报告中展示。  
   - 总评语气示例：「整体完成度不错，结构也完整。下面列出需要修改和可以优化的地方，按重要性排了序，你先看『必改』再改『建议改』。」

2. **优先级用老师常说的说法**  
   - 在报告里把 **High/Medium/Low** 映射成中文短句，例如：  
     - High → **必改**  
     - Medium → **建议修改**  
     - Low → **可选优化**  
   - 在每条问题的标题或 badge 旁显示「必改/建议修改/可选优化」，必要时保留英文标签（如给管理员看）。

3. **案头用语微调**  
   - 将「🤖 AI 修改建议」改为「📝 修改建议」或「批改意见」，弱化「AI」、强化「批改」感。  
   - 将「原文片段/描述」改为「出处/原文」或「相关原文」，更贴近老师批注习惯。  
   - 类别名称可保留「规范一致性」「逻辑一致性」「图文一致性」，若希望更贴近学生用语，可加副标题，如「规范一致性问题（格式与结构）」。

4. **顺序与分组**  
   - 按「先必改、再建议改、再可选优化」排序；同一优先级内再按页码或章节排序。  
   - 这样学生打开报告会先看到「必须改的」，更符合老师「先抓重点」的习惯。

---

### 3.3 第三层：数据结构与流程（可选扩展）

若希望长期做得更细，可以在**数据**上做一点扩展，报告层只做展示：

1. **每条 issue 增加「老师口吻」字段（二选一或都做）**  
   - `teacher_style_suggestion`：与现有 `suggestion` 并存，专门存一句老师口吻的修改建议；报告优先展示该字段，若无则回退到 `suggestion`。  
   - 或直接在 prompt 里要求把「老师口吻」写到现有 `suggestion`，不新增字段。

2. **总评字段**  
   - 在 review JSON 中增加 `overall_comment`（2–3 句），由审查流程中某一步 LLM 根据全部 issues 生成，报告在「详细修改建议」前展示。

3. **优先级中文**  
   - 在 JSON 中为每条 issue 增加 `priority_cn`（如「必改」「建议修改」「可选优化」），或由报告层根据 `severity` 自动映射，无需改 Agent 输出。

---

## 四、建议落地顺序

1. **先做 Prompt 层**  
   - 在规范性、逻辑、目录、视觉等 prompt 中统一加入「老师口吻」的规则与示例，只改 `suggestion`（和必要时 `quote`）的**内容**。  
   - 不改 JSON 结构、不改报告模板，即可明显改善「读起来像不像老师」的感受。

2. **再做报告展示层**  
   - 在 `generate_report.py` 中：  
     - 将「🤖 AI 修改建议」改为「📝 修改建议」或「批改意见」；  
     - 将「原文片段/描述」改为「出处/原文」；  
     - 将 High/Medium/Low 在界面上显示为「必改/建议修改/可选优化」；  
     - 问题列表按优先级（再按页码）排序。  
   - 若有总评数据（如后续在 review 中生成 `overall_comment`），在「详细修改建议」前增加总评区块。

3. **最后视需要做数据与流程扩展**  
   - 若总评希望更贴切，再在 review 流程中增加「根据全部 issues 生成 2–3 句总评」的一步，并写入 JSON、在报告中展示。  
   - 若希望每条建议都保留「机器版 + 老师版」，再考虑 `teacher_style_suggestion` 等字段。

---

## 五、小结

| 现状 | 老师批改 | 改进重点 |
|------|----------|----------|
| 无总评，直接列问题 | 常有 1–2 句总评 | 增加总评区块（可由规则或 LLM 生成） |
| 「🤖 AI 修改建议」、条款式建议 | 温和、可操作、先给一句改法 | Prompt 层统一「老师口吻」；报告层改案头用语 |
| 仅 High/Medium/Low | 必改 / 建议改 / 可选优化 | 报告层映射并排序 |
| 几乎只提问题 | 常「肯定再批评」 | 在 prompt 中鼓励先肯定再提建议（尤其逻辑/语言类） |

按「Prompt 优先 → 报告展示 → 数据与流程扩展」的顺序做，可以在不大改架构的前提下，让批改**更像老师**：既有规范性和准确性，又更易读、更贴近学生的阅读预期。
